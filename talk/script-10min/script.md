## 1. 인트로

안녕하세요. 「AI와 똥손 개발자를 위한 디자인 가이드」라는 주제로 발표하게 된 김해준입니다.

저는 개발자이기 때문에 디자인을 엄청 잘하는 방법을 알려드리지는 못합니다. 하지만 급하게, 임시로 화면을 뽑아서 봐야 한다던지, 사이드 프로젝트라던지 개발자 level에서 생각보다 디자인을 요구하는 경우가 많아, "디자인을 조금 더 개발자답게 다룰 수는 없을까?"라는 고민에서 시작한 이야기를 해보려고 합니다.

## 2. AI 디자인의 문제 — 개발자와 AI의 공통점

그나마 다행인 점은, 요즘 AI가 빠르게 발전하면서 디자인도 어느 정도 AI에게 맡길 수 있게 됐다는 점입니다.

그런데 AI에게 디자인을 맡겨보면 한 가지 문제가 있습니다. 똑같은 걸 요청해도 매번 조금씩 다른 느낌의 결과물이 나오기도 하고, 가끔은 딱 봐도 뭔가 어색한, 소위 말하는 'AI스러운 디자인'이 나오기도 합니다. 그럼 이런 문제를 어떻게 줄일 수 있을까요?

결국 AI에게 그냥 "예쁘게 만들어줘"라고 맡기는 게 아니라, 우리가 먼저 디자인이 어떤 원리로 만들어지는지 어느 정도 이해하고 있어야 합니다.

왜냐하면 개발자와 AI에게는 의외의 공통점이 하나 있기 때문입니다. 둘 다 디자인을 시키면… 조금 불안합니다. 디자인 감각에만 맡기면 결과물이 계속 달라질 수 있다는 거죠.

그렇다면 감각에 의존하지 않고도 괜찮은 디자인을 만들려면 어떻게 해야 할까요?

## 3. 감각 대신 공식화

저희는 개발자니까 익숙한 방법이 있습니다. 감각을 믿지 말고, 공식화하는 겁니다.

색상도 규칙으로 만들고, 간격도 규칙으로 만들고, Radius도 규칙으로 만듭니다. 그리고 이렇게 만들어진 규칙을 AI에게 전달하는 겁니다.

## 4. 어떤 규칙을 정의해야 하나

그럼 어떤 규칙부터 정의해야 할까요? 저는 보통 다음 다섯 가지를 가장 먼저 봅니다.

- **Color** — 비율, 팔레트, 상태별 색상
- **Typography** — 폰트, 크기 체계
- **Spacing / Layout** — 간격 단위, 그리드
- **Radius** — 모서리 값
- **Component State** — Hover/Pressed 같은 상태별 규칙

오늘은 이 중에서 실제로 효과가 가장 컸던 Color를 사례 중심으로 자세히 보고, 나머지는 뒤에서 정리해서 안내해 드리겠습니다.

## 5. Color① — 60-30-10, 토스·네이버·당근

디자인에도 나름의 공식이 있습니다. 대표적으로 색상을 배분할 때 흔히 쓰는 6대3대1, 즉 60-30-10 비율이 있습니다.

실제 대기업 사례를 보면, 토스는 10%의 파란색·30%의 구분된 영역·60%의 배경으로, 네이버는 10%의 초록색·30%의 카드 영역·60%의 배경으로, 당근은 10%의 주황색·30%의 회색 영역·나머지 배경으로 구성되어 있습니다.

공통적으로 대부분을 무채색이 차지합니다. 무난하고 다른 색과 잘 어울리며 가독성이 좋기 때문입니다. 보조색은 배경색에 가까울 수도, Primary 색에 가까울 수도 있습니다.

## 6. Color② — Primary 선정과 팔레트

10% 정도를 차지하는 Primary 색은 브랜드의 가치관을 나타내는 색입니다. 그래서 디자인을 시작할 때 가장 먼저 할 일은 브랜드를 대표하는 색 하나를 고르는 것입니다.

Primary 색을 정했다면 HSL의 L(명도)값을 조정해서 단계별 팔레트를 만들 수 있습니다. 이미 검증된 사이트의 팔레트를 가져와도 무방하고, 결과물은 Tailwind나 CSS 토큰으로 저장해서 사용합니다.

이때 팔레트 위에 올라가는 글자색은 명암비 4.5 이상(WCAG AA 기준)을 만족하는 흰색/검정 중 하나를 선택합니다.

## 7. Color③ — 상태색과 보조 팔레트

만들어진 팔레트에서 상태별 색상도 지정할 수 있습니다. 기본이 Primary-50이라면 Hover는 60, Pressed는 70처럼 일정 간격으로 올리되, 명암비가 갑자기 반전되거나 큰 폭으로 뛰지 않도록 합니다.

배경은 레이어 개념으로 관리합니다 — 기준(bg-0) 위로 2겹 정도(bg-1, bg-2)까지 사용을 권장하며, 별도로 미리 정의해둡니다.

그리고 Primary 외에 Success/Warning/Danger/Info 같은 보조 팔레트도 미리 정의해둡니다.

## 8. Color④ — 시스템 색상 → 컴포넌트 매핑

이렇게 만든 시스템 색상을 각 컴포넌트가 어떤 팔레트/레벨을 쓸지 명시적으로 매핑합니다. 예를 들어 `Button/Primary/Default = Primary-50`, `Alert/Danger/Background = Danger-10` 같은 식입니다.

## 9. 나머지 규칙은 레포에

Color 외에도 Typography(폰트 소스·rem 기준값·다국어), Radius(하나의 값으로 통일), Icon(라이브러리 하나로 통일), Layout/Spacing(최대 너비·Gutter/Column·8px 간격 단위·반응형 기준점), 이미지/모달/텍스트 말줄임까지 같은 방식으로 규칙화할 수 있습니다.

오늘은 시간 관계상 다 다루지 못하지만, 이 규칙들은 전부 Repository의 `framework/specs/`에 지금 본 것과 같은 형식으로 정리되어 있습니다. 궁금하신 분들은 마지막에 안내해드릴 링크에서 확인하실 수 있습니다.

## 10. 전환① — 규칙에서 디자인 토큰으로

이제 지금까지 정의한 규칙들을 실제로 다룰 수 있는 형태로 옮겨야 합니다. 첫 단계는 토큰화입니다.

지금까지 배운 것들을 종합하면 최근 유명한 shadcn처럼 색상을 시맨틱 토큰으로 표현할 수 있습니다.

```css
--color-primary: var(--primary-50);
--color-primary-hover: var(--primary-60);
--color-primary-pressed: var(--primary-70);
--color-bg: var(--neutral-0);
--color-bg-layer-1: var(--neutral-2);
```

이렇게 규칙 하나하나가 변수 하나로 바뀌면, 이 여러 규칙과 조합이 모여 설정에 따라 디자인을 수정할 수 있는 디자인 시스템이 만들어집니다.

## 11. 전환② — 토큰에서 Tailwind, 그리고 코드로

CSS 변수로 만든 토큰은 Tailwind 설정에 그대로 연결할 수 있습니다.

```js
// tailwind.config.js
colors: {
  primary: {
    DEFAULT: 'var(--color-primary)',
    hover: 'var(--color-primary-hover)',
  },
},
borderRadius: {
  DEFAULT: 'var(--radius-base)',
},
```

이렇게 연결해두면 컴포넌트 코드에서는 `bg-primary hover:bg-primary-hover rounded`처럼 클래스 이름만으로 규칙을 그대로 지키게 됩니다. 개발자가 매번 hex 값이나 px 값을 새로 판단할 필요가 없어지는 거죠.

## 12. 전환③ — 규칙에서 AI Markdown 컨텍스트로

여기까지 왔으면 이 규칙을 AI에게도 그대로 전달할 수 있습니다. AI가 지켜야 하는 규칙을 Markdown 파일로 관리하고, 이를 Stitch나 Claude Design 같은 AI에 입력하면 일관된 디자인을 생성할 수 있게 됩니다.

이때 규칙을 얼마나 구체적으로 명시하느냐에 따라 결과의 안정성이 달라집니다. "예쁘게 만들어줘" 같은 한 줄 지시보다, 색상 비율·팔레트 단계·상태값·간격 단위까지 구체적인 숫자로 명시할수록 매번 비슷한 결과가 나옵니다.

이런 시스템이 있으면 MCP를 사용하거나 AI에게 명령을 내릴 때도 결과의 정확도가 올라갑니다.

## 13. Before / After

실제로 비교해보겠습니다. (A) 규칙 없이 "토스 스타일의 모바일 금융 앱 홈 화면을 디자인해줘"라고 한 줄로 요청했을 때와, (B) 지금까지 만든 규칙을 Markdown으로 정리해서 전달했을 때의 결과입니다.

> [화면] A/B 비교 캡처 — 준비 방법은 `talk/demo/scenario.md` 참고

색상 비율, Radius 일관성, 간격 정렬 상태를 짚어보면 차이가 뚜렷하게 드러납니다. 결국 중요한 것은 단순히 "예쁜 화면을 만들어줘"라고 하는 것이 아니라, AI가 따라야 할 규칙을 미리 만들어 전달하는 것입니다.

## 15. 마무리

AI가 디자인을 해주기 때문에 개발자가 디자인을 몰라도 되는 것은 아닙니다.

오히려 AI가 화면을 만들어주는 시대이기 때문에 어떤 결과가 좋은 결과인지 판단하고, 어떤 규칙을 지켜야 하는지 정의하는 능력이 중요해지고 있습니다.

개발자가 디자이너처럼 Figma를 잘 다루거나 감각적으로 예쁜 색을 고를 필요는 없습니다. 대신 디자인을 규칙으로 이해하고, 그 규칙을 시스템으로 만들고, AI가 이해할 수 있도록 전달할 수 있어야 합니다.

결국 AI 시대에 개발자에게 필요한 디자인 능력은 "잘 그리는 능력"보다 "잘 정의하는 능력"입니다.

감사합니다.
