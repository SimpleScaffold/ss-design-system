# improve — 기존 디자인 시스템 진단·개선

이미 토큰화까지 끝난 프로젝트(자체 디자인 시스템이 있거나 `plan`/`transform`을 거친 프로젝트)를 `framework/specs/`와 `validation/accessibility-checklist.md` 기준으로 진단하고, 실제로 고칠 가치가 있는 항목만 골라 개선안을 내는 스킬. `plan`·`transform`이 "0에서 만드는" 스킬이라면, `improve`는 "이미 있는 걸 더 낫게 만드는" 스킬이다.

## 언제 쓰나

- 디자인 시스템은 있는데 시간이 지나며 조금씩 어긋난 값이 쌓였을 때
- 다른 시스템(KRDS/Material/Ant Design 등)의 접근 방식과 비교해서 우리 시스템에 빠진 부분을 찾고 싶을 때
- 새 컴포넌트를 추가하기 전에 기존 계약이 일관적인지 먼저 점검하고 싶을 때

## 절차

1. **전체 스캔** — `validation/accessibility-checklist.md`의 §2~§6을 순서대로 돌며 위반 항목을 전부 수집한다. 이 단계는 넓게, 얕게 — 판단하지 않고 모으기만 한다.
2. **심각도 분류** — 수집한 항목을 아래 기준으로 나눈다.
   - **사용성 문제** (예: 대비 기준 미달, Focus-visible 누락) — 실제 사용자가 겪는 문제라 우선순위 최상위.
   - **일관성 문제** (예: 컴포넌트마다 다른 radius, `--color-primary`와 `--primary`가 섞임, hover를 파일마다 다르게 파생) — 눈에 띄지만 당장 기능은 멀쩡한 경우. 색은 [`prompts/framework/color-tokens.md`](../../prompts/framework/color-tokens.md) 이름과 맞는지만 본다.
   - **확장성 문제** (예: 팔레트 단계가 부족해 새 컴포넌트를 못 만듦) — 지금 당장은 문제가 아니지만 다음 작업을 막는 경우.
3. **비교 참고** — 필요하면 `framework/adapters/{krds,material,ant-design}/`나 `references/design-systems/`를 참고해 "다른 시스템은 이 문제를 어떻게 다루는지" 확인한다. 그대로 베끼지 않고 우리 프로젝트의 제약(플랫폼, 팀 규모)에 맞게 조정한다.
4. **개선안 작성** — 심각도별로 "무엇을, 왜, 어떻게" 3줄로 정리한다. 개선안은 항상 기존 토큰 체계를 깨지 않는 선에서 제안한다 — 팔레트를 통째로 바꾸는 제안보다 "레벨 하나만 추가", "예외 규칙 하나만 문서화" 쪽을 우선한다.
5. **우선순위 합의** — 팀과 함께 무엇부터 고칠지 정한다. `improve`는 발견과 제안까지가 역할이고, 실제 반영은 `transform`의 컴포넌트 단위 치환 절차를 그대로 따른다.

## 출력

- 심각도별로 분류된 위반 항목 목록 (파일/컴포넌트 위치 포함)
- 각 항목의 개선안 (무엇을/왜/어떻게)
- 우선순위가 매겨진 실행 목록 — 바로 `transform`의 입력으로 넘길 수 있는 형태

## 주의

- 발견한 모든 항목을 한 번에 고치려 하지 않는다 — §2의 분류를 반드시 거쳐 우선순위 없는 리스트를 그대로 던지지 않는다.
- "다른 시스템은 이렇게 한다"는 근거만으로 바꾸지 않는다 — §3은 비교 참고일 뿐, 우리 프로젝트에 맞는지 §4에서 다시 판단한다.
