# transform — 기존 화면을 토큰 체계로 전환

이미 화면은 있지만 하드코딩된 hex/px 값이 흩어져 있는 기존 코드베이스를 `framework/specs/`가 정의한 토큰 체계로 옮기는 스킬. `plan`이 "규칙을 새로 만드는" 스킬이라면, `transform`은 "이미 짜여진 코드에서 규칙을 역으로 뽑아내고 그 규칙으로 코드를 다시 쓰는" 스킬이다.

## 언제 쓰나

- 화면은 다 만들었는데 색상/간격이 파일마다 미묘하게 다른 게 뒤늦게 보일 때
- 여러 명이 각자 감으로 작업해서 쌓인 레거시 스타일을 정리할 때
- 디자인 시스템 없이 시작한 프로젝트가 커져서 더 이상 그렇게 유지할 수 없을 때

## 절차

1. **현재 값 수집** — 코드베이스에서 실제 쓰이는 hex 색상, px 간격/radius, 폰트 크기를 전부 뽑아 빈도순으로 나열한다. (예: `#3182F6`이 47곳, `#3183F7`이 3곳 — 후자는 오타/실수일 가능성이 높다.)
2. **팔레트 역산** — 가장 많이 쓰인 색을 Primary 후보로 놓고, `tokens/colors.md`의 HSL L값 규칙으로 10단계 팔레트를 만든 뒤, 수집한 실제 값들이 그 팔레트의 어느 레벨에 가장 가까운지 매핑한다. 팔레트 밖으로 크게 벗어나는 값은 "의도된 예외"인지 "그냥 어긋난 값"인지 확인이 필요한 항목으로 표시한다.
3. **간격/Radius 역산** — 수집한 px 값을 8px 단위(`spacing.md`) · 단일 radius(`radius.md`) 기준으로 반올림 매핑한다. 반올림 폭이 큰 값(예: 13px → 8px or 16px 어느 쪽인지 애매한 경우)은 사람이 판단할 목록으로 따로 뺀다.
4. **토큰 파일 생성** — 2~3단계 결과로 `tokens/colors.md` §9 형식의 CSS 커스텀 프로퍼티 파일을 만든다.
5. **컴포넌트별 치환** — `components/component-contract.md` 구조에 맞춰 컴포넌트 단위로 하드코딩 값을 토큰 참조로 치환한다. 한 번에 전체를 바꾸지 않고 컴포넌트 단위로 끊어서 진행 — 중간에 깨진 화면을 바로 찾을 수 있게 한다.
6. **잔여 값 정리** — 팔레트/토큰 어디에도 매핑되지 않는 값(2단계·3단계에서 "사람이 판단할 목록"으로 뺀 것들)을 마지막에 검토해서 토큰에 새로 추가하거나, 실수였다면 가장 가까운 토큰으로 교정한다.

## 출력

- 실제 값 → 토큰 매핑 표 (전환 전/후 대조용, 리뷰 근거로 남긴다)
- 치환이 끝난 컴포넌트 코드
- `validation/accessibility-checklist.md`로 전환 후 대비·간격이 여전히 기준을 만족하는지 확인한 결과

## 주의

- 기존 값을 팔레트에 우겨넣지 말 것 — 실제로 자주 쓰이는데 팔레트에서 너무 멀리 떨어진 값이 있다면, 그건 팔레트가 이 서비스의 실제 요구를 놓치고 있다는 신호일 수 있다. 이 경우 토큰을 값에 맞춰 조정하는 것이 맞을 때도 있다(무조건 코드를 토큰에 맞추는 것이 목표가 아니다).
- 한 번에 전체 코드베이스를 바꾸려 하지 말 것 — §5처럼 컴포넌트 단위로 끊어서 검증하며 진행한다.
