# 멀티 스킨 토큰 — 한 컴포넌트 라이브러리, 여러 브랜드

> [`README.md`](./README.md)의 익명화 고지 참고. 실제 스코프/속성 이름 대신 일반화한 이름(`.skin-root`, `[data-skin]`)을 쓴다.
> 관련: [`token-architecture.md`](./token-architecture.md), [`framework/specs/tokens/colors.md`](../../framework/specs/tokens/colors.md) §3(팔레트 생성)·§12(다크모드는 재배정)

## 문제 — 같은 컴포넌트로 다른 브랜드를 보여줘야 한다

여러 고객사·프로젝트·서브 브랜드를 하나의 컴포넌트 라이브러리로 지원해야 하는 경우가 있다. 컴포넌트를 프로젝트마다 복제하면 유지보수가 두 배, 세 배로 늘어난다. [`token-architecture.md`](./token-architecture.md)의 3-tier 구조를 한 단계 더 밀어붙이면, 컴포넌트를 하나만 두고 **토큰 계층만 프로젝트별로 다시 선언**해서 해결할 수 있다.

## 해법 — 스코프 단위로 시맨틱 토큰 재선언

핵심 아이디어는 간단하다. 전역 `:root`가 아니라 **특정 스코프 안에서만** 같은 시맨틱 이름을 다시 정의한다.

```css
/* 전역 기본값 (스킨 없음) */
:root {
  --primary: var(--color-neutral-900);
  --background: var(--color-neutral-0);
}

/* 스킨 B — 이 스코프 안에서만 시맨틱 이름이 다른 원시값을 가리킨다 */
.skin-root,
[data-skin] {
  --primary: var(--skin-b-accent-9);
  --background: var(--skin-b-neutral-1);
  /* 이하 shadcn 시맨틱 이름 전부를 이 스코프 값으로 재선언 */
}
```

shadcn 컴포넌트는 `bg-primary`처럼 이름만 참조하므로, 이 스코프 안에 렌더링되기만 하면 **컴포넌트 코드를 한 줄도 바꾸지 않고** 다른 브랜드로 보인다. 스킨을 적용하는 React 쪽 코드는 이 클래스/속성을 감싸는 Provider 컴포넌트 하나로 충분하다.

## 함정 — 포탈(Portal)은 트리 밖에 렌더링된다

`.skin-root` 같은 클래스 선택자만 쓰면 한 가지가 새어나간다 — 다이얼로그, 툴팁, 드롭다운처럼 리액트 포탈로 `document.body` 바로 아래에 렌더링되는 요소는 원래 트리의 클래스 스코프 밖에 있다. 그래서 CSS 선택자를 두 개 병행해야 한다.

```css
.skin-root,
[data-skin] {
  /* 토큰 재선언 */
}
```

- `.skin-root` — 일반적인 트리 안 요소용.
- `[data-skin]` — 포탈로 렌더링되는 요소에 별도로 붙이는 data attribute. Provider가 포탈 컨테이너에도 이 속성을 함께 심어줘야 다이얼로그 안의 버튼도 같은 스킨을 받는다.

이 함정은 "토큰이 CSS 상속을 타고 내려간다"는 가정이 리액트 포탈에서는 깨진다는 점에서 온다 — CSS 상속 자체는 유지되지만, DOM 트리 상 위치가 달라지므로 클래스 기반 스코프가 물리적으로 닿지 않는다.

## Radix Colors 12-step 팔레트 — 더 세분화된 명도 체계

공통 스펙 §3은 "명도만 조정해서 단계별 팔레트를 만든다"고 규정하지만 몇 단계로 나눌지는 정하지 않는다. 실무 관찰 사례는 [Radix Colors](https://www.radix-ui.com/colors) 방법론을 따라 **12단계**로 세분화하고, 각 단계에 역할을 미리 고정해둔다.

| 단계 | 역할 |
| --- | --- |
| 1 | 앱 배경 |
| 2 | 서브틀 배경 |
| 3 | 컴포넌트 배경 |
| 4 | Hover 배경 |
| 5 | Active 배경 |
| 6 | 서브틀 보더 |
| 7 | UI 보더 / 포커스 링 |
| 8 | Hover 보더 |
| 9 | Solid — 브랜드색 고정 지점 |
| 10 | Hover Solid |
| 11 | 저대비 텍스트 (WCAG AA 4.5:1 이상 보장) |
| 12 | 고대비 텍스트 |

역할이 고정돼 있으므로 "이 요소는 몇 단계를 써야 하나" 같은 판단을 매번 새로 할 필요가 없다 — 공통 스펙 [`component-contract.md`](../../framework/specs/components/component-contract.md)가 "감으로 고르지 않는다"고 말하는 것과 같은 취지를, 팔레트 레벨에서 미리 해결해두는 것이다.

## hex 앵커 몇 개로 48단계를 코드로 파생시키기

브랜드마다 12단계 전체를 디자이너가 손으로 정하는 건 비효율적이다. 실무 관찰 사례는 브랜드색 하나(9단계, "Solid" 고정 지점)만 hex로 받고, 나머지 11단계는 코드로 계산한다.

방법론(값 자체는 예시):

1. hex를 HSL로 변환해 색상각(H)·채도(S)·명도(L)를 얻는다.
2. 라이트/다크 각각에 대해 **12단계 명도 커브 템플릿**을 미리 정해둔다 (예: 라이트는 99%에서 15%로, 다크는 5%에서 93%로 이동하는 고정된 수열).
3. 9단계(Solid)는 원본 hex의 H·S·L을 그대로 쓴다 — 유일하게 고정되는 지점.
4. 10단계(Hover Solid)는 9단계에서 명도를 살짝(예: 6pt) hover 방향으로 이동시켜 파생한다.
5. 나머지 단계는 템플릿의 명도값을 그대로 쓰되, 채도는 원본 채도에 단계별 비율(채도 곡선)을 곱해서 줄인다 — 배경에 가까운 단계일수록 채도를 더 낮춘다.

이 방법으로 **브랜드색 4개(Primary/Success/Warning/Danger 각 1개 hex)** 만 있으면 라이트 12단계 × 다크 12단계 = 96개 값을 전부 코드에서 생성할 수 있다. 디자이너가 새 브랜드를 추가할 때 조정하는 입력값은 hex 4개뿐이고, 나머지는 항상 같은 공식이 보장한다 — 팔레트 자체가 하나의 "규칙"이 되는 셈이다.

Neutral 계열은 예외다 — 밝기만 바뀌는 다른 팔레트와 달리 색상각 자체가 단계마다 미세하게 이동하는 경우가 있다(브랜드 정체성을 위해 배경은 살짝 녹색 기운, 텍스트는 살짝 청색 기운처럼). 이런 곡선은 공식으로 일반화하기 어려워서, 실무에서는 이 계열만 12단계 값을 상수로 고정해두고 공식 파생 대상에서 제외하는 경우가 있다.
