# 규칙을 적어두는 것과 지켜지게 만드는 것은 다른 문제다

> [`README.md`](./README.md)의 익명화 고지 참고.
> 관련: [`framework/specs/validation/accessibility-checklist.md`](../../framework/specs/validation/accessibility-checklist.md), [`framework/specs/pipeline.md`](../../framework/specs/pipeline.md)

이 사례 연구 전체가 "규칙을 어떻게 md로, 토큰으로, 코드로 옮기는가"를 다루지만, 관찰된 프로젝트에는 그 반대 사례도 있었다 — **규칙은 문서화돼 있는데 실제로는 지켜지지 않거나, 심지어 규칙이 가리키는 문서 자체가 없는** 경우다. 발표가 강조하는 "AI/개발자에게 규칙을 명시적으로 전달해야 한다"는 메시지는, 뒤집어 보면 "명시적으로 전달되지 않거나 검증되지 않는 규칙은 지켜지지 않는다"는 뜻이기도 하다. 이 문서는 그 반증 사례를 정리한다.

## 사례 1 — 인용된 규칙 파일이 실제로는 없었다

여러 문서(루트 가이드, 패키지별 가이드)가 "간격 규칙 상세는 이 경로를 참고하라"며 특정 규칙 파일 경로를 반복해서 가리키고 있었다. 그런데 그 경로를 실제로 열어보면 파일이 존재하지 않았다 — git 히스토리에도 없어서, 애초에 만들어진 적이 없거나 삭제된 뒤 참조만 남은 것으로 보였다.

이런 일이 생기는 이유는 단순하다: 문서 간 링크는 사람이 직접 관리하고, 파일을 지우거나 옮길 때 그 문서를 가리키는 다른 문서까지 함께 고치는 걸 강제하는 장치가 없기 때문이다. `framework/specs/pipeline.md`의 "값은 한 방향으로만 흐른다" 원칙과 비슷하게, **문서 간 참조도 깨지지 않으려면 검증 장치가 있어야 한다** — 예를 들어 CI에서 마크다운 링크가 실제로 존재하는 파일을 가리키는지 확인하는 단계.

## 사례 2 — 규칙은 있는데 자동으로 검사되지 않는다

[`spacing-grid.md`](./spacing-grid.md)의 "4px 그리드 우선" 규칙, [`component-conventions.md`](./component-conventions.md)의 "슬롯 CSS엔 hex 금지" 규칙 모두 여러 문서에 반복해서 적혀 있었다. 하지만 실제 코드를 뒤져보면:

- 홀수 px(`3px`, `18px` 등)를 쓰는 곳이 실제로 존재했다 — 심지어 **컴포넌트 생성 CLI가 만들어낸 코드**에서도 나왔다.
- 원시 hex 값을 컴포넌트에 직접 박아 넣은 곳이 한 군데 있었다(문서상으로는 금지된 패턴).

이 프로젝트의 자동화 수준을 정리하면:

| 계층 | 있는 것 | 없는 것 |
| --- | --- | --- |
| 포맷팅 | Tailwind 클래스 순서 정렬(커밋 전 자동 실행) | — |
| 정적 분석 | 일반 코드 컨벤션(화살표 함수, import 경로 등) | 4px 그리드 위반을 잡는 규칙, hex 직접 사용을 잡는 규칙, CSS 전용 린터 |
| CI | — | 파이프라인 자체가 없어서, 위 규칙들이 빌드를 막을 방법이 없다 |

즉 자동화된 것은 "이미 옳게 짠 코드의 형식을 정돈하는 것"뿐이고, "애초에 규칙을 어긴 코드를 잡아내는 것"은 전혀 자동화돼 있지 않았다. 사람이 코드 리뷰에서 매번 눈으로 확인해야 하는 구조다.

## 왜 CLI가 생성한 코드조차 규칙을 어겼나

컴포넌트 생성기(shadcn CLI)는 공식 기본 스타일을 그대로 찍어내는데, 그 기본 스타일 자체가 이 프로젝트의 4px 그리드 규칙 기준으로는 정확히 맞아떨어지지 않는 값(포커스 링 두께 등)을 쓰고 있었다. 프로젝트 고유 규칙은 외부 생성기가 알 도리가 없으므로, **생성된 코드를 그대로 두면 자동으로 규칙을 어기게 된다.** 이 간극을 메우려면 둘 중 하나가 필요하다 — 생성 직후 프로젝트 규칙에 맞게 후처리하는 스크립트를 두거나, 어긴 코드를 잡아내는 린트 규칙을 두는 것.

## 그래서 얻는 결론

1. **규칙 문서화 ≠ 규칙 준수.** md 파일에 규칙을 적어두는 것은 시작일 뿐이고, 그 자체로는 아무것도 강제하지 못한다.
2. **자동 검증이 없는 규칙은 생성기·시간·사람의 실수 앞에서 반드시 깨진다.** 이번 사례에서는 공식 CLI가 만든 코드조차 예외가 아니었다.
3. **강제 수단에는 위계가 있다** — [`component-conventions.md`](./component-conventions.md)의 "style prop을 타입에서 제거" 사례처럼 컴파일 타임에 막는 것이 가장 강하고, 그다음이 CI에서 실패시키는 린트, 그다음이 코드 리뷰 체크리스트, 가장 약한 것이 "문서에 적어두고 사람이 기억하길 바라는 것"이다. 이 프로젝트의 대부분 규칙은 가장 약한 단계에 머물러 있었다.

이 결론은 `framework/specs/validation/`이 왜 별도 스펙 카테고리로 존재하는지, 그리고 발표에서 "AI에게 규칙을 md로 전달하는 것"이 왜 충분조건이 아니라 필요조건인지를 뒷받침하는 실제 근거다 — 규칙을 AI나 사람에게 아무리 명확하게 전달해도, 그 결과를 검증하는 단계가 없으면 결국 같은 방식으로 깨진다.
